## Purpose

Establish one timestamp discipline for consequential records across GitHub, Notion, Linear, and thesis materials so that significant observations, decisions, declarations, milestones, and status changes carry a consistent provenance marker.

## Canonical display formats

### Human-facing

`YYYY-MM-DD · h:mm AM/PM TZ`

Example:

`2026-08-27 · 9:33 PM EDT`

### Machine-readable

`YYYY-MM-DDTHH:MM:SS±HH:MM`

Example:

`2026-08-27T21:33:00-04:00`

### UTC companion

Use when cross-system ordering, export, or machine comparison benefits from a timezone-neutral value:

`YYYY-MM-DDTHH:MM:SSZ`

Example:

`2026-08-28T01:33:00Z`

## Required record fields

A consequential timestamped record SHOULD preserve:

- **Timestamp** — when the observation, decision, declaration, milestone, or status change was recorded.
- **Event** — what changed or what was established.
- **Status** — one of `OBSERVATION`, `DECISION`, `DECLARATION`, `MILESTONE`, or `STATUS CHANGE`, with a more specific bounded disposition when needed.
- **Authority / source** — who or what supplied the governing decision or evidence.
- **Evidence boundary** — what the timestamp establishes and what it does not establish.
- **Reference / checkpoint** — commit SHA, issue, document, artifact, or other traceable record when available.

## Governing rules

1. Consequential records receive timestamps; casual conversation does not require them.
2. A timestamp establishes record timing, not the origin of an idea, private understanding, authorship, priority, novelty, ownership, or truth of the underlying claim.
3. Git commit time, Notion edit time, Linear update time, and an in-document semantic timestamp are distinct evidence surfaces. None silently substitutes for another.
4. Cross-system alignment uses the same effective semantic timestamp when the records describe the same authorized event. Each platform may also preserve its native created/updated time.
5. Corrections preserve the earlier record where possible and add a new correction timestamp; they do not silently rewrite historical timing.
6. When a timestamp is supplied by a human source rather than independently generated by the recording system, that provenance SHOULD be preserved when material.
7. Timezone is explicit. Prefer the local abbreviation together with an ISO-8601 offset; preserve UTC when machine ordering matters.
8. A timestamp never creates authority. Capability, permission, execution, reassessment, ownership, and external acceptance remain independently bounded.
9. Existing Git SHAs and artifact hashes remain the stronger identity references for exact repository or file state; timestamping supplements them rather than replacing them.

## Cross-platform application

### GitHub

Use the canonical human-facing timestamp in governance and assessment records and retain the ISO-8601 form where exact machine comparison is useful. Commit SHA remains the canonical repository-state identifier.

### Notion

Use the same semantic timestamp and status vocabulary for aligned governance notes. Notion's native `created_time` / `last_edited_time` are platform metadata, not replacements for the semantic record timestamp.

### Linear

Use the same semantic timestamp in project, issue, document, milestone, or status-update records that represent consequential decisions or state changes. Linear's native activity time remains separate platform metadata.

### Thesis records

Use timestamping as provenance for consequential thesis amendments, observations, decisions, declarations, milestones, and status changes. Preserve the thesis interpretive boundary:

`TIMESTAMP != ORIGIN OF THOUGHT OR UNDERSTANDING`
